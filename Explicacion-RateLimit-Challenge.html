Rate limit de /deviceintegrity/initiate

El hallazgo original proponía limitarlo por deviceid y sessionappid para que nadie llene Redis de challenges. Eso es necesario, pero no basta: esos dos valores los manda el cliente y un atacante los rota. Aquí van ejemplos de cómo se llena Redis y qué haríamos de verdad.

Ojo, en una frase: limitar solo por headers del cliente es un límite que el atacante elige no cumplir. El challenge tiene que nacer de una sesión autenticada, vivir como una sola clave por sesión (se sobrescribe, no se acumula) y tener tres techos: sesión, IP y global. El servicio replica el límite, por si APIM no aplica.
  1. No crear un UUID nuevo en Redis por cada initiate. La clave es integrity:ch:{sessionId}, con TTL de 120 s.
  2. El sessionId sale del JWT validado, no del header sessionappid.
  3. En APIM: 6 llamadas / 60 s por sesión, 30 / 60 s por IP, y un techo global. Respuesta 429.
  4. En el servicio: el mismo contador en Redis, más maxmemory en la instancia de challenges.

1. Qué se guarda hoy

Tier 1 pide un challenge al servicio. El servicio genera un nonce, lo guarda en Redis 120 segundos, de un solo uso, y lo devuelve. Cada initiate que llega escribe en Redis. Si la clave es un UUID distinto cada vez, Redis crece con el tráfico, no con el número de usuarios.

Sin límite: un script llena Redis

Vulnerable
Ejemplo numérico. Cada challenge ocupa, con overhead de Redis, unos 800 bytes. TTL = 120 s. Memoria pico ≈ peticiones/s × 120 × 800 bytes.

Con 2 000 peticiones/s durante 2 minutos, Redis llega a ~192 MB solo de challenges, y sigue igual de lleno mientras el ataque dure. Un bot más grande o varias réplicas del script lo multiplican. El daño no es solo memoria: CPU de Redis, conexiones, hilos del servicio y cuota de APIM.

2. Por qué deviceid + sessionappid no cierran el ataque

Esos dos headers son parte de los headers comunes del documento. La app los envía. El servidor, si no los autentica, no puede saber si son reales. Un atacante que rote el par obtiene un contador nuevo en cada ráfaga.

Los números 6 / 30 / 400 son un punto de partida. Un cliente legítimo pide un challenge por operación Tier 1, no por cada tap. Con 6 por minuto sobra para reintentos y no alcanza para un flood. Hay que validarlos con el pico medido en MONITOR.

La misma sesión no acumula challenges

Clave única
Por qué el overwrite importa más que el número 6 Aunque el rate limit falle o se evada un rato, Redis tiene como máximo una clave por sesión viva. El tamaño queda acotado por sesiones concurrentes (usuarios reales + sesiones robadas), no por peticiones por segundo. El flood de UUIDs deja de existir.

4. Ejemplos de implementación

4.1 Política de APIM en /deviceintegrity/initiate

rate-limit-by-key limita llamadas por una clave arbitraria durante un periodo de como máximo 300 segundos. Si se supera, APIM responde 429 Too Many Requests. Fuente: Azure API Management: rate-limit-by-key. El Renewal máximo de 300 s obliga a usar quota-by-key si se quiere un techo diario. 
<policies>
  <inbound>
    <base />
    <!-- 1. Sesión autenticada. El sid no se lee del header. -->
    <validate-jwt header-name="Authorization" failed-validation-httpcode="401"
                  require-expiration-time="true" require-signed-tokens="true">
      <openid-config url="{{session-jwks-url}}" />
      <audiences><audience>{{session-audience}}</audience></audiences>
    </validate-jwt>
    <set-variable name="sid"
      value="@{
        var jwt = context.Request.Headers.GetValueOrDefault("Authorization","").Split(' ').Last();
        var p = jwt.Split('.')[1].PadRight(jwt.Split('.')[1].Length + (4 - jwt.Split('.')[1].Length % 4) % 4, '=');
        var json = Encoding.UTF8.GetString(Convert.FromBase64String(p.Replace('-','+').Replace('_','/')));
        return (String)((JObject)Newtonsoft.Json.JsonConvert.DeserializeObject(json))["sid"];
      }" />
    <choose>
      <when condition="@(string.IsNullOrEmpty((string)context.Variables["sid"]))">
        <return-response><set-status code="401" reason="Unauthorized" /></return-response>
      </when>
    </choose>

    <!-- 2. Techo por sesión -->
    <rate-limit-by-key calls="6" renewal-period="60"
        counter-key="@("init|sid|" + (string)context.Variables["sid"])"
        retry-after-header-name="Retry-After" />
    <!-- 3. Techo por IP -->
    <rate-limit-by-key calls="30" renewal-period="60"
        counter-key="@("init|ip|" + context.Request.IpAddress)" />
    <!-- 4. Techo global de este operation -->
    <rate-limit-by-key calls="400" renewal-period="1"
        counter-key="init|global" />
  </inbound>
  <backend><base /></backend>
  <outbound><base /></outbound>
  <on-error><base /></on-error>
</policies>
Detalles de APIM que conviene no olvidar El contador es por gateway y no es exacto al 100 % (lo dice Microsoft). En un APIM multi-región cada región cuenta aparte: el techo efectivo se multiplica. increment-condition con expresiones se evalúa al final del outbound y el 429 puede llegar una petición tarde; para este endpoint es mejor contar todas las llamadas, no solo las 200. Consumption tier no tiene rate-limit-by-key.

4.2 Servicio: overwrite + límite en Redis

public Challenge initiate(Session s) {
    if (s == null || s.sid == null) throw unauthorized();

    String rl = "rl:init:" + s.sid;
    Long n = redis.incr(rl);
    if (n == 1) redis.expire(rl, 60);
    if (n > 6) throw tooManyRequests(60);

    String nonce = randomUrlSafe(32);                 // 32 bytes → cabe en Huawei (16–66) y en Play
    String body = json(nonce, s.deviceId, s.sid, now());
    redis.set("integrity:ch:" + s.sid, body, ex(120)); // overwrite: una clave, no un UUID nuevo
    return new Challenge(s.sid, nonce, 120);
}

public Challenge consume(Session s, String presentedNonce) {
    String raw = redis.getdel("integrity:ch:" + s.sid); // atómico, un solo uso
    if (raw == null) throw deny("CHALLENGE_MISSING");
    Challenge ch = parse(raw);
    if (!constantTimeEquals(ch.nonce, presentedNonce)) throw deny("CHALLENGE_MISMATCH");
    return ch;
}

4.3 Redis: acotar el daño

# instancia o DB 1 solo para challenges

256 MB, a 800 bytes por clave, son unas 300 000 sesiones con challenge vivo. Eso es un techo de incidentes, no de operación normal. La alerta de memoria al 60 % avisa antes de que Redis empiece a tirar claves.
