iOS sin App Attest: qué haríamos

Propuesta para el caso en que DCAppAttestService.isSupported devuelve false o App Attest falla, que el documento de smp-device-integrity-service todavía no define.

Propuesta en una frase: "no soportado" lo declara el cliente, así que nunca debe significar "sin validación". El dispositivo pasa a postura UNVERIFIED, que bloquea Tier 1 y deja Tier 2 en modo DEGRADED. Además, reducimos al mínimo los casos legítimos para que cualquier volumen fuera de lo normal se vea como ataque.
  1. Eliminar los casos legítimos evitables: no publicar la app de iPhone en Macs con Apple silicon y no exponer operaciones protegidas desde extensiones.
  2. Distinguir tres situaciones: no soportado, falla temporal de Apple y clave inválida. Cada una tiene un tratamiento distinto.
  3. Evitar la degradación: un dispositivo que ya enroló App Attest no puede volver a declarar "no soportado".
  4. Postura UNVERIFIED: Tier 1 se deniega o exige un step-up aprobado, y Tier 2 queda en DEGRADED.
  5. Medir y alertar el porcentaje de peticiones iOS sin App Attest.

1. Cuándo App Attest no está disponible (según Apple)

This includes Mac Catalyst apps, and iOS or iPadOS apps running on Apple silicon." Fuente: DCAppAttestService.isSupported
"Most extensions don't support App Attest. The generateKey method fails when you call it from an app extension, regardless of the value of isSupported." Fuente: misma página.

2. El riesgo: "no soportado" como bypass

El valor de isSupported lo lee la app en el dispositivo. El servidor solo se entera de lo que la app le dice, por ejemplo con un header X-INTEGRITY-UNSUPPORTED: true o simplemente sin enviar aserción. Un atacante con una app modificada, un jailbreak o un script puede declarar "no soportado" y ahorrarse App Attest. Es el mismo patrón de "elegir el control más débil" que vimos con X-INTEGRITY-PLATFORM.

Por eso la regla base "No soportado" nunca equivale a ALLOW. Se trata como ausencia de evidencia, igual que un token que falta, y la decisión la toma la política por tier.

3.1 Evitar la degradación: "una vez enrolado, siempre enrolado"

Cuando un dispositivo enrola App Attest con éxito, queda registrado (deviceid → ios, appAttest = true, con el mismo registro de plataforma que vimos en la explicación de suplantación de plataforma). A partir de ahí:

  • Si ese deviceid o esa sesión llegan sin aserción, o declarando "no soportado", se responde DENY. Un iPhone no pierde el Secure Enclave.
  • Si la clave ya no sirve (invalidKey, por reinstalación o restauración), el camino es volver a enrolar, no degradar.

3.3 Falla temporal de Apple durante el enrolamiento

El enrolamiento (attestKey) sí llama a los servidores de Apple. Si fallan, la app reintenta con backoff (por ejemplo 3 intentos en minutos) y en el siguiente inicio. Mientras tanto, el dispositivo queda UNVERIFIED temporal, con la misma política de la tabla. Ese estado tiene un plazo máximo: si después de ese plazo el dispositivo sigue sin enrolar, se trata como el caso 3.2 y se alerta.

4. Medición y alertas

Una vez eliminados los casos evitables (Mac, extensiones y simulador), el volumen legítimo de iOS sin App Attest debería ser cercano a cero. Por eso la métrica es un buen detector:

5. ¿Y DeviceCheck como alternativa?

DeviceCheck (DCDevice.generateToken) da otra señal de Apple, pero no prueba que la petición venga de la app legítima ni ata nada a la petición. Solo permite guardar 2 bits por dispositivo en Apple, que sirven por ejemplo para marcar un dispositivo como fraudulento. Puede complementar la postura UNVERIFIED como señal de fraude, pero no la convierte en VERIFIED.

6. Cambios en la app y en el servicio

6.1 App (Swift, ilustrativo)

enum AttestState { case enrolled(keyId: String), unsupported, retryLater, needsReenroll }

func ensureAttestation() async -> AttestState {
    let service = DCAppAttestService.shared
    guard service.isSupported else { return .unsupported }        // se informa al servidor, no se salta nada
    if let keyId = keychain.keyId { return .enrolled(keyId: keyId) }
    do {
        let keyId = try await service.generateKey()
        let challenge = try await api.initiate(purpose: .enroll)
        let attestation = try await service.attestKey(keyId, clientDataHash: sha256(challenge.value))
        try await api.enroll(keyId: keyId, attestation: attestation, challengeId: challenge.id)
        keychain.keyId = keyId
        return .enrolled(keyId: keyId)
    } catch let e as DCError where e.code == .serverUnavailable {
        return .retryLater                                          // backoff; UNVERIFIED temporal
    } catch let e as DCError where e.code == .invalidKey {
        keychain.keyId = nil
        return .needsReenroll
    } catch {
        return .retryLater
    }
}
// Las peticiones protegidas de un dispositivo sin aserción envían X-INTEGRITY-ATTEST-STATE (unsupported | retry_later)
// para la métrica. El servidor nunca lo usa para conceder ALLOW.

6.2 Servicio (pseudocódigo)

Decision evaluateIos(Req r, Tier tier) {
    DeviceRecord dev = registry.find(r.deviceId);

    if (r.assertion == null) {                                       // sin evidencia: "no soportado" o falla
        if (dev != null && dev.appAttestEnrolled)  return alert(deny("ATTEST_DOWNGRADE"));
        metrics.unverified(r.attestState);
        return tier == TIER_1 ? policy.tier1Unverified()            // DENY o STEP_UP según política aprobada
                              : degraded("POSTURE_UNVERIFIED");
    }
    if (!keys.exists(r.keyId))                     return deny("REENROLL_REQUIRED");  // la app vuelve a enrolar
    return verifyAssertion(r, tier);                                 // flujo normal (hash, firma, counter con ETag)
}
