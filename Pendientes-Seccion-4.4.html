Pendientes de la sección 4.4: postura propuesta

Cuatro políticas que el documento deja abiertas. Sin ellas, ENFORCE no se puede operar: no se sabe qué hacer si Google no responde, qué significa un Named Value vacío, qué hace el backend con SKIPPED ni quién puede apagar un switch.

Las cuatro posturas, en corto.
  1. Caída: fail-closed en Tier 1 (DENY), DEGRADED en Tier 2. Timeouts explícitos en APIM y en el servicio.
  2. Switch de bypass: ausente o inválido significa validar, no apagar ni bloquear todo. Solo un false explícito salta la evaluación.
  3. SKIPPED: el backend procesa, registra el motivo y aplica controles compensatorios. Nunca lo trata como un ALLOW silencioso en operaciones críticas.
  4. Dueño del switch: AppSec opera, Riesgos aprueba, caduca solo (por ejemplo 2 h) si nadie lo renueva.

1. Caída: fail-closed en Tier 1, DEGRADED en Tier 2

Si el servicio no responde, si Google o Huawei no responden, o si se agota la cuota de Play Integrity, hay que decidir antes del incidente. Fail-open convierte una caída en un bypass: un atacante satura el servicio y opera sin integridad. Fail-closed en los dos tiers convierte una caída de Google en una caída de la app Personas.

Timeouts sugeridos (punto de partida, a medir en MONITOR):

  • APIM → servicio: timeout="1" en send-request (1 s; el objetivo es no pasar de ~800 ms de espera útil), ignore-error="true" para aplicar la política en lugar de devolver 500 de APIM.
  • Servicio → Google: 1 500 ms, un reintento. Servicio → Huawei: no hay llamada de red si se verifica el JWS en local (ver HTML de Huawei). Servicio → Apple (solo enrolamiento): 1 500 ms.
  • El tiempo total que ve el cliente no debería pasar de ~2 s en el camino de integridad. Si no, la app ya habrá mostrado error de red.
DEGRADED no es “dejar pasar” El backend, al ver DEGRADED, acorta la sesión, baja montos, sube el peso del motor de fraude y registra el motivo. Si un backend ignora el header, DEGRADED se convierte en fail-open.

2. El bypass no se activa por un Named Value vacío

Hay dos “fail-closed” distintos y el documento los puede mezclar:

Qué está cerradoSi falla la config
Caída del servicio (arriba)La operaciónTier 1 se deniega
Switch de bypass allowintegrityverifyLa puerta para no validarSe sigue validando

Un Named Value ausente, en blanco, con un typo (tru, FALSE mal copiado, 0) no puede significar “bloquear todo el canal” ni “saltar la integridad”. Lo segundo sería un fail-open accidental: alguien borra el Named Value y la app Personas queda sin validación. Lo primero sería una caída autoinfligida.

Solo un false explícito apaga la evaluación

3. Qué hace el backend con SKIPPED

SKIPPED quiere decir “APIM no evaluó”, no “el dispositivo es íntegro”. Hoy el documento no dice qué hace el backend. Si lo trata como ALLOW, el switch de emergencia y la convivencia de versiones antiguas se convierten en un ALLOW silencioso.

SKIPPED llega al backend con un motivo

Postura
Motivo (X-Integrity-Reason)CuándoQué hace el backend
SWITCH_OFFKill switch global o de plataforma en falseProcesa. Log + métrica + mismos controles compensatorios que DEGRADED en Tier 1 (monto, fraude). Alerta si dura más que la caducidad.
MONITORModo MONITOR: se evaluó, no se bloqueaProcesa. Guarda la decisión hipotética para el umbral de ENFORCE.
LEGACY_CLIENTVentana de versiones antiguasProcesa. Límites de monto más bajos en Tier 1. Ver HTML de versiones antiguas.
TIER3Operación fuera de alcanceProcesa sin controles extra de integridad.
Ausente o desconocidoBug o fragmento a mediasTratar como UNVERIFIED / DENY en Tier 1. No es ALLOW.

APIM siempre escribe X-Integrity-Decision y X-Integrity-Reason con override, y firma (ver HTML de spoofing). El backend verifica la firma. Sin firma, no hay SKIPPED de confianza.

4. Dueño del switch, aprobación y caducidad

Los Named Values allowintegrityverify, …android, …huawei y …ios apagan la evaluación. Sin dueño ni caducidad, un incidente de Huawei puede dejar el switch en false semanas.

Apagar un switch es un cambio con caducidad

RolResponsabilidad
DueñoAppSec. Único que cambia el Named Value en APIM (o vía pipeline).

<!-- Caducidad: aunque el switch siga en false, si ya venció se valida -->
<set-variable name="integrityOff" value="@{
  var flag = "{{allowintegrityverify}}".Trim().ToLowerInvariant() == "false";
  var untilRaw = "{{allowintegrityverify-until}}";
  long until;
  if (!flag) return false;
  if (!long.TryParse(untilRaw, out until)) return false; // sin caducidad válida, no se acepta el bypass
  return DateTimeOffset.UtcNow.ToUnixTimeSeconds() < until;
}" />
Sin timestamp de caducidad no hay bypass Así un false olvidado no dura para siempre. El valor allowintegrityverify-until lo escribe el mismo cambio que pone el false.

6. Texto sugerido para la sección 4.4

Políticas de contingencia "Si smp-device-integrity-service, Redis, Cosmos DB o el proveedor no responden dentro del timeout (800 ms APIM→servicio, 1 500 ms servicio→proveedor), Tier 1 se deniega y Tier 2 se responde DEGRADED, con motivo INTEGRITY_SERVICE_UNAVAILABLE, PROVIDER_UNAVAILABLE, PROVIDER_QUOTA o INTEGRITY_STORE_UNAVAILABLE. La cuota agotada de Play Integrity se trata igual que una caída del proveedor. Los Named Values allowintegrityverify* solo desactivan la evaluación con el valor exacto false y un allowintegrityverify-until vigente; ausente, vacío o inválido implica validar. SKIPPED llega al backend con X-Integrity-Reason (SWITCH_OFF, MONITOR, LEGACY_CLIENT, TIER3) y firma; el backend procesa con controles compensatorios y no lo equivale a ALLOW. El switch lo opera AppSec con aprobación de Riesgos, bitácora y caducidad automática de 2 horas."
