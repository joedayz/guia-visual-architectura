¿Cómo se falsifica X-Integrity-Decision y cómo se evita?

Explicación del riesgo en la propuesta de smp-device-integrity-service: el backend de negocio confía en un header que también puede escribir el cliente.

En una frase: el backend de negocio decide si atiende una operación leyendo el header X-Integrity-Decision. Un header HTTP lo puede escribir cualquiera que haga la petición. Si ese valor puede llegar al backend sin que lo haya puesto APIM, el control de integridad deja de existir.
  1. Ataque 1, inyección por APIM: el atacante manda el header desde su propio cliente y APIM lo deja pasar en alguna ruta.
  2. Ataque 2, bypass de APIM: el atacante llega al backend sin pasar por APIM y le manda el header directamente. Como el backend está en la red interna, esto solo es posible desde dentro.
El Ataque 1 es el riesgo principal: usa el camino legítimo a través de APIM, así que la red interna no lo frena. Las dos condiciones del hallazgo cierran cada ataque: APIM borra el header entrante (cierra el 1) y el backend solo acepta tráfico autenticado de APIM (cierra el 2).

1. Flujo correcto (lo que el diseño espera)

La app manda la evidencia de integridad (token, JWS o assertion). APIM se la pasa a smp-device-integrity-service, recibe la decisión y la escribe en X-Integrity-Decision. El backend lee ese header para saber si procesa, restringe o rechaza.

Flujo esperado

Referencia
El supuesto escondido El backend da por hecho que todo X-Integrity-Decision que recibe lo escribió APIM. Nada en el diseño original garantiza ese supuesto, y los dos ataques se apoyan justamente en eso.

2. Ataque 1: el cliente inyecta el header y APIM lo deja pasar

Por defecto, APIM reenvía al backend todos los headers que recibe del cliente. Solo cambia los que una policy toca explícitamente. Así que basta con que exista una ruta en la que la policy no sobrescriba el header.

2.1 Qué manda el atacante

El atacante no necesita la app. Le basta con un proxy (Burp, mitmproxy) sobre un dispositivo rooteado, o directamente curl con un token de sesión válido:

POST /transfers/execute HTTP/1.1 Host: api.ibk.example Authorization: Bearer eyJhbGciOi... (sesión válida del atacante) consumerid: app-personas deviceid: 3f9c... X-INTEGRITY-PLATFORM: android X-TOKEN-INTEGRITY: basura X-Integrity-Decision: ALLOW {"destination_account":"...","amount":"5000.00","currency":"PEN"}

2.2 ¿En qué rutas deja pasar APIM el header?

Si en el camino normal se escribe el header con exists-action="override", el valor del atacante se pisa. El problema aparece en todas las rutas donde APIM no llega a escribirlo:

Ruta en APIMPor qué el header del atacante llega al backend
Operaciones Tier 3No llevan el policy fragment de integridad. APIM reenvía los headers tal cual. Si el backend que atiende Tier 3 comparte librería o filtro con Tier 1 y Tier 2, puede leer el ALLOW del atacante.
Operación nueva sin fragmentAlguien publica un endpoint y olvida incluir el fragment. El backend sí espera el header, y lo recibe del cliente.
Kill switch en falseSi la rama de emergencia no sobrescribe con SKIPPED (por ejemplo, porque solo hace <return-response> o <forward-request>), pasa el valor del cliente.
Fail-open por timeoutSi el servicio de integridad no responde y la rama fail-open reenvía sin escribir el header, el atacante elige la decisión. Además, puede provocar el timeout a propósito.
exists-action="append"El backend recibe ALLOW, DENY o dos headers. Muchos frameworks devuelven el primer valor, que es el del atacante.
Variantes de nombreAPIM trata los nombres sin distinguir mayúsculas, pero un proxy o WAF intermedio puede no hacerlo. Por ejemplo, x-integrity-decision o X_Integrity_Decision (algunos servidores convierten _ en -).

Sin protección: Tier 3, operación sin fragment o fail-open

Vulnerable

Con protección: APIM borra el header al entrar

Mitigado
Control 1: borrar al entrar, en el nivel más alto El borrado va en el scope All APIs (policy global), como primera instrucción de <inbound>. Así aplica también a Tier 3, a operaciones nuevas y a cualquier rama del fragment. Luego, cada rama que reenvía al backend escribe el valor con override, incluidas SKIPPED y la de fail-open (por ejemplo UNVERIFIED).

3. Ataque 2: el atacante se salta APIM

Contexto de la propuesta: todo vive en la red interna de IBK Según el diagrama de despliegue (3.2), smp-device-integrity-service y el backend de negocio están en la red interna. Solo APIM está en la zona expuesta. Por eso este ataque no se puede hacer desde internet: un usuario con la app o con curl no llega al backend sin pasar por APIM. Lo que queda es un riesgo interno, de menor probabilidad, y se trata como defensa en profundidad.

"Red interna" no es lo mismo que "solo APIM". El backend sigue alcanzable por cualquier cosa que ya esté dentro de la red:

  • Un host interno comprometido (malware en un servidor o en la estación de un operador).
  • Otros consumidores internos legítimos que llaman al backend sin pasar por APIM: el BFF (el documento dice que también invoca al servicio), batch, otras aplicaciones del banco.
  • Un proveedor con acceso por VPN o un pod vecino en el mismo cluster.
  • Una exposición accidental, como un FQDN público por defecto del App Service o un ingress mal configurado. En este caso el riesgo vuelve a ser externo.

Por eso el control proporcional es restringir el backend a la subred de APIM, no a toda la red interna. La firma HMAC o mTLS queda como recomendación. Su peso depende de qué tan segmentada esté la red y de si otros consumidores internos llegan al mismo backend.

Sin protección: el backend acepta a cualquiera

Vulnerable

Con protección: el backend exige prueba de que viene de APIM

Mitigado
Control 2: el backend solo acepta tráfico de APIM, en capas
  1. Red: private endpoint o restricción de acceso que solo permita la subred o IP de APIM. Sin FQDN público.
  2. Identidad del llamante: mTLS, con APIM presentando un certificado de cliente que el backend valida.
  3. Integridad del header: APIM firma la decisión con HMAC (decisión, operación, requestId, timestamp) y el backend verifica la firma. Aunque alguien llegue por la red, no puede fabricar una decisión válida.
Como el backend ya está en la red interna, el punto 1 se reduce a limitar el acceso a la subred de APIM. Los puntos 2 y 3 son defensa en profundidad frente a un atacante que ya está dentro.

5. Cómo se implementa

5.1 APIM: policy global (scope All APIs)

<policies>
  <inbound>
    <!-- Primero: nada que venga del cliente puede parecer una decisión de APIM -->
    <set-header name="X-Integrity-Decision" exists-action="delete" />
    <set-header name="X-Integrity-Signature" exists-action="delete" />
    <set-header name="X-Integrity-Timestamp" exists-action="delete" />
    <base />
  </inbound>
  <backend><base /></backend>
  <outbound><base /></outbound>
  <on-error><base /></on-error>
</policies>

5.2 APIM: fragment de integridad (todas las ramas escriben y firman)

<fragment>
  <choose>
    <!-- Solo un "false" explícito apaga la validación; ausente o inválido = validar -->
    <when condition="@("{{allowintegrityverify}}".Trim().ToLower() == "false")">
      <set-variable name="integrityDecision" value="SKIPPED" />
    </when>
    <otherwise>
      <send-request mode="new" response-variable-name="integrityResp" timeout="3" ignore-error="true">
        <set-url>{{integrity-service-url}}/deviceintegrity/evaluate/posture</set-url>
        <set-method>POST</set-method>
        <!-- token, plataforma, resumen de la petición -->
      </send-request>
      <set-variable name="integrityDecision" value="@{
        var r = context.Variables.GetValueOrDefault<IResponse>("integrityResp");
        if (r == null || r.StatusCode != 200) { return "UNVERIFIED"; }  // fail-open controlado
        return r.Body.As<JObject>()["decision"].ToString();
      }" />
    </otherwise>
  </choose>

  <choose>
    <when condition="@((string)context.Variables["integrityDecision"] == "DENY")">
      <return-response><set-status code="403" reason="Forbidden" /></return-response>
    </when>
  </choose>

  <set-variable name="integrityTs" value="@(DateTimeOffset.UtcNow.ToUnixTimeSeconds().ToString())" />

  <!-- Siempre override, nunca append -->
  <set-header name="X-Integrity-Decision" exists-action="override">
    <value>@((string)context.Variables["integrityDecision"])</value>
  </set-header>
  <set-header name="X-Integrity-Timestamp" exists-action="override">
    <value>@((string)context.Variables["integrityTs"])</value>
  </set-header>
  <set-header name="X-Integrity-Signature" exists-action="override">
    <value>@{
      var data = string.Join("|",
        (string)context.Variables["integrityDecision"],
        context.Request.Method,
        context.Request.Url.Path,
        context.RequestId.ToString(),
        (string)context.Variables["integrityTs"]);
      using (var h = new System.Security.Cryptography.HMACSHA256(
               System.Text.Encoding.UTF8.GetBytes("{{integrity-hmac-key}}"))) {
        return Convert.ToBase64String(h.ComputeHash(System.Text.Encoding.UTF8.GetBytes(data)));
      }
    }</value>
  </set-header>
  <set-header name="X-Request-Id" exists-action="override">
    <value>@(context.RequestId.ToString())</value>
  </set-header>
</fragment>

{{integrity-hmac-key}} es un Named Value secreto respaldado por Key Vault. El mismo secreto lo lee el backend desde Key Vault, y se rota en ambos lados.

5.3 Backend: filtro que verifica antes de cualquier lógica de negocio

// Pseudocódigo (Java / Spring), aplicado como filtro a todos los endpoints protegidos
String decision  = req.getHeader("X-Integrity-Decision");
String ts        = req.getHeader("X-Integrity-Timestamp");
String signature = req.getHeader("X-Integrity-Signature");
String requestId = req.getHeader("X-Request-Id");

if (decision == null || signature == null || ts == null) {
    return deny("INTEGRITY_HEADER_MISSING");          // nunca asumir ALLOW
}
if (req.getHeaders("X-Integrity-Decision").size() > 1) {
    return deny("INTEGRITY_HEADER_DUPLICATED");       // defensa contra append
}
if (Math.abs(now() - Long.parseLong(ts)) > 30) {
    return deny("INTEGRITY_HEADER_STALE");            // evita reutilizar una firma vieja
}
String expected = hmacSha256(key, String.join("|",
        decision, req.getMethod(), req.getRequestURI(), requestId, ts));
if (!MessageDigest.isEqual(expected.getBytes(), signature.getBytes())) {
    return deny("INTEGRITY_SIGNATURE_INVALID");       // no viene de APIM
}
switch (decision) {
    case "ALLOW"      -> proceed();
    case "DEGRADED"   -> proceedWithRestrictions();   // solo si la operación tiene restricción aprobada
    case "SKIPPED"    -> proceedAndAudit();           // kill switch activo
    case "UNVERIFIED" -> tier1 ? deny("FAIL_CLOSED") : proceedWithRestrictions();
    default           -> deny("INTEGRITY_DECISION_UNKNOWN");
}

5.4 Red

  • Backend con private endpoint o access restrictions que permitan solo la subred de APIM (VNet integrada).
  • Sin FQDN público alcanzable. Si existe, con restricción explícita y probada.
  • Opcional: mTLS entre APIM y backend (policy authentication-certificate en APIM y validación del certificado en el backend).
