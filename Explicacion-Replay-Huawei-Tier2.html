¿Por qué el nonce local de Huawei en Tier 2 permite replay?

Explicación del riesgo en el flujo Huawei Tier 2 de smp-device-integrity-service y de la propuesta: nonce derivado de la petición y registro de nonces usados en Redis.

En una frase: hoy la app inventa el nonce y el servidor no tiene con qué compararlo. El JWS de Huawei prueba que algún dispositivo sano lo pidió hace poco, pero no para qué petición. Por eso el mismo JWS sirve para muchas peticiones distintas mientras siga dentro de la ventana de frescura.

La propuesta tiene dos partes y hacen falta las dos. Ligar el nonce a la petición impide usar el JWS para otra cosa. Registrarlo en Redis impide usarlo dos veces para la misma cosa.

1. La idea con una analogía

Hoy: un sello en blancoUn notario sella una hoja que dice "documento revisado a las 10:00", pero la hoja no dice qué documento. Quien tenga la hoja puede grapar cualquier documento hasta que se considere "vieja".
Parte 1: el sello dice qué documentoLa hoja ahora incluye la huella del documento. Si la grapas a otro, la huella no coincide y se rechaza.
Parte 2: el sello se anota en un libroLa ventanilla anota cada sello que recibe. Si alguien presenta la misma hoja con el mismo documento una segunda vez, ya figura en el libro y se rechaza.

2. Cómo funciona hoy (diagrama del documento: "Tier 2, nonce local")

Flujo actual de Huawei Tier 2

Referencia

El servicio revisa la firma, la cadena de certificados, timestampMs (frescura), el package, el certDigest y basicIntegrity. Todo eso dice algo del dispositivo, pero nada de la petición. El JWS por dentro se ve así:

{ "nonce": "R2Vu...aleatorio", ← lo inventó la app; el servidor no sabe qué valor esperar "timestampMs": 1762292400000, ← sí se valida (frescura) "apkPackageName": "pe.ibk.personas", "apkCertificateDigestSha256": ["..."], "basicIntegrity": true }
Qué puede comprobar el servidor y qué no Sí comprueba que el JWS es auténtico, de nuestra app, de un dispositivo sano y reciente. No comprueba que el JWS se pidió para esta petición, ni que es la primera vez que lo ve. Esos dos huecos son el replay.

3. Cómo sucedería el ataque

El escenario realista no es robar el JWS de otra persona, porque el tráfico va cifrado con TLS. Lo realista es que el propio atacante lo saque de un dispositivo sano y lo reutilice desde donde quiera:

  1. Tiene un teléfono Huawei sano (sin root) con la app instalada. Ese teléfono saca un JWS válido con basicIntegrity = true.
  2. Copia ese JWS. Lo puede ver en su propio tráfico, porque controla el dispositivo o tiene una app de pruebas.
  3. Durante la ventana de frescura, pega ese mismo JWS en muchas peticiones enviadas desde un script, un emulador o un dispositivo rooteado.
  4. El servicio valida firma, frescura y basicIntegrity, y todo pasa. Cada petición recibe ALLOW.

Ataque: un JWS sano reutilizado en muchas peticiones desde un bot

Vulnerable
Resultado Un solo JWS sano funciona como un pase libre temporal para cualquier operación Tier 2: consultas masivas, scraping de datos, automatización de flujos desde emuladores. Si la ventana de frescura es de 5 minutos, el atacante solo necesita un JWS nuevo cada 5 minutos para mantener funcionando un bot completo.

4. La propuesta

4.1 Parte 1: el nonce se deriva de la petición

En vez de generar un nonce aleatorio, la app lo calcula con los datos de la petición que va a enviar. Es lo mismo que hace iOS con el clientDataHash:

nonce = SHA256( método | ruta | SHA256(cuerpo) | deviceid | timestamp )
  • Da 32 bytes, dentro del rango que acepta SysIntegrity (16 a 66 bytes).
  • La app envía timestamp en X-INTEGRITY-TIMESTAMP, porque el servidor lo necesita para recalcular.
  • deviceid ata el JWS además al dispositivo de la sesión.
  • El servidor recalcula el nonce con la petición que realmente recibió y lo compara con el del JWS. Si el atacante cambia cualquier cosa (ruta, cuerpo, dispositivo, hora), no coincide.

4.2 Parte 2: registrar los nonces usados en Redis

Con la parte 1, el JWS solo sirve para esa petición exacta. Pero esa petición exacta se puede reenviar tal cual (por ejemplo, repetir la misma solicitud cien veces). Para eso, el servicio registra cada nonce aceptado:

SET integrity:huawei:nonce:{nonce} 1 NX EX {ventana_de_frescura_en_segundos}
  → OK   : primera vez, se acepta
  → nil  : ya se usó, DENY NONCE_REPLAYED

El TTL igual a la ventana de frescura es suficiente: pasado ese tiempo, el JWS ya se rechaza por viejo, así que no hace falta guardar el nonce más tiempo. Usar NX hace la operación atómica, de modo que dos peticiones simultáneas no pueden pasar con el mismo nonce.

5. ¿Por qué hacen falta las dos partes?

Intento del atacanteHoy (nonce aleatorio)Solo RedisSolo nonce ligadoAmbas
Usar un JWS en muchas peticiones distintasPasaSolo pasa la primera, pero esa puede ser cualquier peticiónBloqueadoBloqueado
Reenviar la misma petición muchas vecesPasaBloqueadoPasa durante la ventanaBloqueado
Sacar un JWS en un dispositivo sano y usarlo en una petición del botPasaPasaSolo si el dispositivo sano calcula el nonce sobre la petición del bot (riesgo residual)Igual: riesgo residual
Riesgo residual: el relay Ninguna atestación evita del todo que un atacante con un dispositivo sano lo use como "firmador" de peticiones que arma en otro lado: le pasa el nonce, el dispositivo sano saca el JWS y él lo pega en la petición del bot. La propuesta lo vuelve caro, porque cada petición necesita un JWS nuevo hecho sobre ella y no hay reutilización. Para Tier 2 suele ser aceptable. El resto lo cubren el límite de peticiones por deviceid, la detección de anomalías y, para lo crítico, Tier 1 con challenge del servidor. Conviene dejarlo documentado como riesgo aceptado.

6. Validación completa en el servicio

Orden de validación para Huawei Tier 2

Resumen

El orden importa: Redis se escribe al final, solo cuando todo lo demás pasó. Si se registrara antes, un atacante podría "quemar" nonces legítimos mandando JWS inválidos con el mismo valor.

7. Cómo se implementa

7.1 App (Kotlin, ilustrativo)

val ts = System.currentTimeMillis().toString()
val bodyHash = sha256Hex(bodyBytes)
val nonce = sha256Bytes(listOf(method, path, bodyHash, deviceId, ts).joinToString("|"))

SafetyDetect.getClient(context)
    .sysIntegrity(nonce, appId)
    .addOnSuccessListener { resp ->
        request.header("X-TOKEN-INTEGRITY", resp.result)       // JWS
               .header("X-INTEGRITY-PLATFORM", "huawei")
               .header("X-INTEGRITY-TIMESTAMP", ts)
    }

7.2 APIM: enviar al servicio el resumen de la petición

<set-variable name="bodyHash" value="@{
  var body = context.Request.Body?.As<string>(preserveContent: true) ?? "";
  using (var sha = System.Security.Cryptography.SHA256.Create()) {
    return BitConverter.ToString(sha.ComputeHash(System.Text.Encoding.UTF8.GetBytes(body)))
                       .Replace("-", "").ToLower();
  }
}" />
<send-request mode="new" response-variable-name="integrityResp" timeout="3" ignore-error="true">
  <set-url>{{integrity-service-url}}/deviceintegrity/evaluate/posture</set-url>
  <set-method>POST</set-method>
  <set-header name="Content-Type" exists-action="override"><value>application/json</value></set-header>
  <set-body>@(new JObject(
      new JProperty("platform",  "huawei"),
      new JProperty("evidence",  context.Request.Headers.GetValueOrDefault("X-TOKEN-INTEGRITY", "")),
      new JProperty("method",    context.Request.Method),
      new JProperty("path",      context.Request.OriginalUrl.Path),
      new JProperty("bodyHash",  (string)context.Variables["bodyHash"]),
      new JProperty("deviceId",  context.Request.Headers.GetValueOrDefault("deviceid", "")),
      new JProperty("timestamp", context.Request.Headers.GetValueOrDefault("X-INTEGRITY-TIMESTAMP", ""))
  ).ToString())</set-body>
</send-request>

La app y APIM deben usar la misma ruta (la que ve el cliente, OriginalUrl) y la misma serialización del cuerpo, byte a byte. Conviene acordarlo por escrito, igual que el payload canónico de Tier 1.

7.3 Servicio (pseudocódigo)

Decision evaluateHuaweiPosture(Req r) {
    Jws jws = verifySignatureAndChain(r.evidence);            // cadena Huawei, hostname del cert
    if (jws == null)                         return deny("JWS_INVALID");

    long now = clock.millis();
    long ts  = parseLong(r.timestamp);
    if (abs(now - ts) > WINDOW_MS)           return deny("TIMESTAMP_STALE");
    if (abs(now - jws.timestampMs) > WINDOW_MS) return deny("JWS_STALE");

    if (!jws.apkPackageName.equals(PACKAGE) || !CERT_DIGESTS.contains(jws.certDigest))
                                             return deny("APP_MISMATCH");

    byte[] expected = sha256(join("|", r.method, r.path, r.bodyHash, r.deviceId, r.timestamp));
    if (!constantTimeEquals(expected, base64Decode(jws.nonce)))
                                             return deny("NONCE_MISMATCH");     // otra petición

    if (!jws.basicIntegrity)                 return policyDecision("BASIC_INTEGRITY_FALSE");

    // Al final: solo se registra un nonce de una petición que ya pasó todo lo anterior
    boolean first = redis.set("integrity:huawei:nonce:" + hex(expected), "1",
                              SetParams.setParams().nx().ex(WINDOW_MS / 1000));
    if (!first)                              return deny("NONCE_REPLAYED");     // misma petición repetida

    return allow();
}

Ventana de frescuraHoy no está definida. Para Tier 2 se sugieren 60 a 120 s, igual que el TTL del challenge de Tier 1, con hasta 30 s de tolerancia por desfase de reloj.
Campos del noncemétodo | ruta | SHA256(cuerpo) | deviceid | timestamp, con separador y codificación fijados por escrito.
Redis no disponibleSi no se puede registrar el nonce, no hay protección contra replay. Hay que definir si se responde DENY o DEGRADED; entra en las políticas de contingencia pendientes.
Reintentos legítimos de la appUn reintento por timeout de red reenvía el mismo nonce y será rechazado. La app debe sacar un JWS nuevo en cada reintento, o el backend debe aceptar el reintento por idempotencia.
