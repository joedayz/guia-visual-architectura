iOS Tier 2: ¿por qué el servicio debe recalcular el clientDataHash?

Explicación del riesgo en el flujo "iOS Tier 2, assertion sin challenge por request" de smp-device-integrity-service: una aserción válida pegada a otra petición.

En una frase: la aserción de App Attest es una firma del dispositivo sobre un clientDataHash. Si el servicio verifica la firma usando un hash que le manda la app, solo comprueba que el dispositivo firmó algo, no que firmó esta petición. Hay que recalcular el hash con los datos que APIM realmente recibió.

El counter no lo evita: impide usar una aserción dos veces, pero no impide usarla una vez en la petición equivocada.

1. La idea con una analogía

La firmaEl cliente firma un papel que dice "huella del documento: 7F3A...". La firma es auténtica, de su puño y letra.
Lo que se revisa hoyEl cajero comprueba que la firma es del cliente y que corresponde a la huella "7F3A..." escrita en el papel. Todo cuadra.
Lo que faltaNadie calcula la huella del documento que realmente se entregó. Si alguien cambia el documento y deja el papel firmado, nadie lo nota.

2. Cómo se verifica una aserción de App Attest

Esto es lo que dice Apple ("Validating apps that connect to your server", paso de assertion):

// En el iPhone clientDataHash = SHA256(clientData) // clientData = datos de la petición assertion = generateAssertion(keyId, clientDataHash) // firma en el Secure Enclave // En el servidor 1. clientDataHash = SHA256(clientData) ← ¿de dónde sale clientData? 2. nonce = SHA256(authenticatorData || clientDataHash) 3. Verificar la firma de la assertion sobre nonce con la clave pública de keyId 4. rpIdHash == SHA256(teamId.bundleId) 5. counter > counter guardado
El punto clave El servidor no puede verificar la firma sin un clientDataHash. Así que la implementación siempre va a tener uno. La pregunta es de dónde lo saca:
  • Vulnerable: la app lo manda en un header (por ejemplo X-INTEGRITY-CLIENT-DATA-HASH), o manda clientData y nadie lo compara con la petición real.
  • Correcto: el servicio lo arma él mismo con el método, la ruta, el cuerpo y el timestamp de la petición que APIM recibió.
El diagrama del documento dice "verifica firma, rpIdHash y counter", pero no indica de dónde sale el hash. Ahí está el hueco.

4. Cómo sucedería el ataque

4.1 Ataque A: modificar la petición después de firmarla

El atacante usa la app real en su iPhone real (App Attest lo exige), pero pone un proxy entre la app y APIM. La app firma la petición original y el proxy cambia el cuerpo antes de enviarla. La aserción sigue siendo válida, porque se verifica contra el hash que viajó en el header, que no cambió.

POST /beneficiaries/add (Tier 2) X-TOKEN-INTEGRITY: o2NmbXRv... (assertion real del iPhone) X-INTEGRITY-KEY-ID: k9Zx... X-INTEGRITY-CLIENT-DATA-HASH: 7F3A... (hash de la petición ORIGINAL) {"alias":"mamá","account":"ATACANTE-0099"} ← antes decía "...-1234"

Ataque A: el proxy cambia el cuerpo y la aserción sigue pasando

Vulnerable

4.2 Ataque B: trasplantar aserciones a un bot

El atacante usa su iPhone legítimo como "fábrica" de aserciones. Cada aserción, con su hash, se pega en una petición distinta armada por un bot o un script. El counter no lo frena, porque cada aserción tiene un counter mayor que la anterior y se usa una sola vez.

Ataque B: aserciones de un iPhone real usadas por un bot

Vulnerable

4.3 Ataque C: acumular aserciones para usarlas después

La aserción no lleva hora: Apple no pone timestamp dentro. Si el timestamp no forma parte del clientData y el servidor no lo valida, el atacante puede generar 1000 aserciones hoy y gastarlas en orden la semana siguiente. El counter seguirá subiendo y todas pasarán.

Resultado El control de integridad de iOS Tier 2 queda en "existe un iPhone legítimo en algún lado", y no en "esta petición viene de la app legítima, sin modificar". Para Tier 2 eso habilita bots, scraping y cambios de parámetros sobre peticiones firmadas.

5. La corrección

5.1 Qué cambia

  1. La app arma el clientData con datos de la petición y un timestamp, y firma su hash. Envía la aserción, el keyId y el timestamp, pero no envía el hash.
  2. APIM manda al servicio el resumen de la petición que recibió: método, ruta, SHA256(cuerpo), deviceid y timestamp.
  3. El servicio recalcula el clientDataHash con esos datos y verifica la firma contra ese hash. Si alguien cambió la petición, la firma no valida.
  4. El servicio comprueba que el timestamp esté dentro de la ventana de frescura (por ejemplo 60 a 120 s). Eso cierra el Ataque C.
  5. El counter se actualiza con escritura condicional (ETag de Cosmos DB), para que dos peticiones simultáneas no pasen con el mismo counter.
clientData     = método | ruta | SHA256(cuerpo) | deviceid | timestamp
clientDataHash = SHA256(clientData)

Flujo corregido: el servicio recalcula el clientDataHash

Riesgo residual Con un iPhone con jailbreak, el atacante podría hacer que la app legítima firme peticiones arbitrarias (relay). App Attest no detecta jailbreak por sí solo. Es un riesgo conocido de la plataforma: lo mitigan el límite de peticiones por keyId y deviceid, el campo opcional de riesgo de fraude de Apple (receipt) y Tier 1 para lo crítico. Conviene documentarlo como riesgo aceptado para Tier 2.

8.3 Servicio (pseudocódigo)

Decision evaluateIosPosture(Req r) {
    long now = clock.millis();
    if (abs(now - parseLong(r.timestamp)) > WINDOW_MS)  return deny("TIMESTAMP_STALE");

    Device d = cosmos.read(r.keyId);                      // clave pública, counter, deviceId, etag
    if (d == null)                                        return deny("KEY_NOT_ENROLLED");
    if (!d.deviceId.equals(r.deviceId))                   return deny("DEVICE_MISMATCH");

    Assertion a = cbor.decode(base64(r.assertion));       // signature + authenticatorData

    // El hash se arma aquí, con la petición real; nunca se toma del cliente
    byte[] clientDataHash = sha256(join("|", r.method, r.path, r.bodyHash, r.deviceId, r.timestamp));
    byte[] nonce = sha256(concat(a.authenticatorData, clientDataHash));
    if (!ecdsaVerify(d.publicKey, nonce, a.signature))    return deny("ASSERTION_INVALID");

    if (!a.rpIdHash().equals(sha256(TEAM_ID + "." + BUNDLE_ID))) return deny("APP_MISMATCH");

    long counter = a.counter();
    if (counter <= d.counter)                             return deny("COUNTER_REPLAYED");
    if (!cosmos.replaceIfMatch(r.keyId, d.withCounter(counter), d.etag))
                                                          return deny("COUNTER_RACE");

    return allow();
}

10. Ajustes al documento

  • En el diagrama iOS Tier 2, cambiar "verifica firma, rpIdHash y counter mayor al guardado" por: "recalcula clientDataHash con la petición recibida, verifica firma, rpIdHash, frescura del timestamp y counter mayor al guardado".
  • Agregar X-INTEGRITY-TIMESTAMP a los headers de iOS Tier 2.
  • Indicar que APIM envía al servicio método, ruta, SHA256(cuerpo), deviceid y timestamp.
  • Definir por escrito la serialización del clientData (separador, codificación, ruta y cuerpo), igual que el payload canónico de Tier 1.
  • Documentar el relay con jailbreak como riesgo residual aceptado.
