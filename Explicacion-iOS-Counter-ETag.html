iOS: ¿por qué el counter en Cosmos DB debe actualizarse con ETag?

Explicación de la condición de carrera en la validación de aserciones de App Attest en smp-device-integrity-service (Tier 1 y Tier 2).

En una frase: el servicio hace tres pasos separados: lee el counter, compara y escribe. Si dos peticiones llegan al mismo tiempo, las dos leen el mismo valor viejo antes de que cualquiera escriba, y las dos pasan la comparación.

Esto tiene dos consecuencias. La misma aserción se acepta varias veces, de modo que el counter deja de proteger contra replay. Y el counter puede retroceder, lo que permite reutilizar aserciones que ya se habían usado. La corrección es escribir solo si el documento no cambió desde que se leyó: ETag con If-Match, que es la concurrencia optimista de Cosmos DB.

1. La idea con una analogía

El talonarioCada cheque tiene un número. El banco anota el último número cobrado y solo acepta números mayores.
Dos cajeros a la vezLlegan dos copias del cheque 6. Los dos cajeros miran el libro al mismo tiempo, ven "último: 5", y los dos pagan. Luego los dos anotan 6.
Con ETagEl libro tiene un sello de versión. Un cajero solo puede anotar si el sello sigue igual que cuando lo leyó. El segundo cajero ve que el sello cambió, vuelve a leer, ve "último: 6" y rechaza el cheque.

2. Por qué existe el counter

Cada aserción de App Attest lleva un counter que el Secure Enclave incrementa en cada uso de la clave. El servicio guarda en Cosmos DB el último counter aceptado por keyId y rechaza cualquier aserción con un counter menor o igual. Así, una aserción solo sirve una vez. En iOS Tier 2 es la única protección contra replay, porque no hay challenge ni Redis.

// Diagrama del documento: "Lee clave pública y counter" → "Verifica ... counter mayor al guardado" → "Actualiza counter"
stored = cosmos.read(keyId).counter        // 1. leer
if (assertion.counter <= stored) deny()     // 2. comparar
cosmos.upsert(keyId, counter = assertion.counter)   // 3. escribir  ← sin condición
El hueco Entre el paso 1 y el paso 3 pasan milisegundos: se verifica la firma, se calcula el hash y hay una ida y vuelta a Cosmos DB. Cualquier petición que lea en ese intervalo ve el valor viejo. Además, el servicio corre en varias réplicas, así que un lock en memoria no lo resuelve.

3. Problema 1: la misma aserción pasa varias veces

El atacante captura una aserción válida (counter 6) y la envía 20 veces en paralelo, por ejemplo con un script. Cada petición cae en una réplica distinta del servicio.

4. Problema 2: el counter retrocede

Este caso ni siquiera requiere un atacante para ocurrir. La app manda dos peticiones protegidas casi a la vez (assertion 6 y assertion 7) y llegan en orden distinto a réplicas distintas. Si la 7 escribe primero y la 6 después, el counter guardado queda en 6, aunque ya se aceptó la 7.

Resultado
  • Tier 2: una aserción capturada se puede usar N veces si se envía en ráfaga. Como el clientDataHash liga la aserción a una petición concreta, el efecto es repetir esa petición: duplicar una operación o multiplicar el volumen de un bot con una sola aserción.
  • Tier 1: el challenge de Redis, consumido con GETDEL atómico, ya frena el replay. Pero el counter que retrocede deja el estado de la clave inconsistente para el resto de peticiones.
  • Detección: los logs muestran ALLOW con el mismo counter repetido, o counters que bajan. Si nadie lo monitorea, pasa inadvertido.

5. La corrección: concurrencia optimista con ETag

Cosmos DB asigna a cada documento un _etag que cambia en cada escritura. Si se escribe con If-Match: <etag leído>, Cosmos DB solo acepta la escritura cuando nadie modificó el documento en medio. Si alguien lo hizo, responde 412 Precondition Failed. Entonces el servicio vuelve a leer y a evaluar con el valor nuevo.

Resumen
Efecto secundario: peticiones legítimas en paralelo Con la corrección, si la app envía dos peticiones protegidas a la vez y la de counter mayor llega primero, la otra se rechaza (COUNTER_REPLAYED), aunque sea legítima. Es el comportamiento correcto según el modelo de App Attest, pero conviene acordar con el equipo móvil:
  • no enviar en paralelo peticiones protegidas firmadas con la misma clave, o serializar la generación de la aserción y el envío;
  • ante un 403 con COUNTER_REPLAYED de una petición propia, generar una aserción nueva y reintentar una vez.

6. Cómo se implementa

6.1 Opción A: leer, validar y reemplazar con If-Match (Java SDK)

static final int MAX_RETRIES = 3;

Decision updateCounter(String keyId, long assertionCounter) {
    for (int i = 0; i < MAX_RETRIES; i++) {
        CosmosItemResponse<DeviceKey> read = container.readItem(keyId, new PartitionKey(keyId), DeviceKey.class);
        DeviceKey key = read.getItem();

        if (assertionCounter <= key.getCounter()) {
            return deny("COUNTER_REPLAYED");                     // otra petición ya usó este counter o uno mayor
        }

        key.setCounter(assertionCounter);
        try {
            container.replaceItem(key, keyId, new PartitionKey(keyId),
                new CosmosItemRequestOptions().setIfMatchETag(read.getETag()));
            return allow();
        } catch (CosmosException e) {
            if (e.getStatusCode() != 412) throw e;               // 412: alguien escribió en medio, se vuelve a leer
        }
    }
    return deny("COUNTER_CONTENTION");
}

6.2 Opción B: patch condicional en una sola llamada

Cosmos DB permite un patch con predicado de filtro: la escritura solo se aplica si la condición se cumple en el servidor, en forma atómica. Así se evita la lectura previa del counter (la clave pública igual se lee para verificar la firma).

try {
    container.patchItem(keyId, new PartitionKey(keyId),
        CosmosPatchOperations.create().set("/counter", assertionCounter),
        new CosmosPatchItemRequestOptions()
            .setFilterPredicate("FROM c WHERE c.counter < " + assertionCounter),
        DeviceKey.class);
    return allow();
} catch (CosmosException e) {
    if (e.getStatusCode() == 412) return deny("COUNTER_REPLAYED");   // el predicado no se cumplió
    throw e;
}

6.3 Detalles del contenedor

  • La clave de partición es /keyId. Todas las operaciones de una clave caen en la misma partición lógica, que es donde el ETag y el patch condicional garantizan atomicidad.
  • Con una sola región de escritura, la escritura condicional se evalúa en la región que escribe y la garantía se cumple sin importar el nivel de consistencia. Si la cuenta usa escrituras multi-región, dos regiones pueden aceptar escrituras en paralelo y el conflicto se resuelve después (por defecto, gana la última escritura). En ese caso el ETag no basta, y conviene que este contenedor escriba en una sola región.
  • El mismo patrón aplica al enrolamiento: crear el documento con createItem (falla con 409 si el keyId ya existe), nunca con upsert, para que nadie pueda sobrescribir una clave enrolada.
