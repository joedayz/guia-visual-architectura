Android Tier 2: ¿por qué hace falta requestHash aunque no haya challenge?

Explicación del riesgo en el flujo "Tier 2, sin challenge" de Google Play Integrity en smp-device-integrity-service, y de la validación de requestHash, timestampMillis y requestPackageName.

En una frase: el token de Play Integrity dice "este dispositivo y esta app son legítimos", pero si se pide sin requestHash no dice para qué petición. El servicio no puede detectar que el token se usó en una petición modificada o armada por un bot.

La corrección tiene tres partes. La app pone SHA256(método | ruta | SHA256(cuerpo) | deviceid | timestamp) en el requestHash. El servicio recalcula ese hash con la petición real. Y el servicio valida timestampMillis (frescura) y requestPackageName (nuestra app).

1. La idea con una analogía

El token es un certificado médicoDice "esta persona está sana", firmado por un médico de confianza (Google). Es auténtico.
Sin requestHashEl certificado no dice para qué trámite es. Sirve para cualquier ventanilla, y cualquiera que lo tenga puede presentarlo.
Con requestHashEl certificado dice "válido para el trámite 7F3A..., emitido a las 10:00". Si lo presentas en otro trámite o al día siguiente, se rechaza.

2. Qué trae el token de Play Integrity

Al descifrarlo con decodeIntegrityToken, el servicio recibe algo así:

{ "requestDetails": { "requestPackageName": "pe.ibk.personas", ← debe ser nuestra app "requestHash": "", ← vacío hoy en Tier 2: el token no está ligado a nada "timestampMillis": "1762292400000" ← cuándo se generó; hay que validarlo }, "appIntegrity": { "appRecognitionVerdict": "PLAY_RECOGNIZED", "packageName": "pe.ibk.personas", ... }, "deviceIntegrity": { "deviceRecognitionVerdict": ["MEETS_DEVICE_INTEGRITY"] }, "accountDetails": { ... } }

Las tres partes de requestDetails responden a preguntas distintas:

CampoPregunta que respondeSi no se valida
requestHash¿Este token se pidió para esta petición?El token sirve para cualquier petición: se puede modificar el cuerpo o trasplantar el token a un bot.
timestampMillis¿Se pidió hace poco?Un token sano de hace horas o días sigue sirviendo.
requestPackageName¿Lo pidió nuestra app?Se aceptan tokens pedidos desde otra app. Es una defensa en profundidad, junto con appIntegrity.
Qué dice Google En las standard requests, el requestHash es el mecanismo previsto para proteger la petición contra manipulación. Google recomienda llenarlo con un resumen de los datos relevantes de la acción, también cuando no hay challenge del servidor. La documentación también menciona una mitigación automática de replay en este tipo de petición, pero no liga el token a una petición concreta: eso solo lo hace el requestHash.

4. Cómo sucedería el ataque

4.1 Ataque A: modificar la petición después de obtener el token

El atacante usa la app real en un Android sano, así que el token sale limpio. Pero pone un proxy entre la app y APIM y cambia el cuerpo de la petición. Como el token no lleva ningún hash de la petición, el servicio no tiene con qué detectar el cambio.

POST /beneficiaries/add (Tier 2) X-TOKEN-INTEGRITY: eyJhbGciOiJBMjU2S1ci... (token sano, sin requestHash) X-INTEGRITY-PLATFORM: android {"alias":"mamá","account":"ATACANTE-0099"} ← la app había enviado "...-1234"

Ataque A: el proxy cambia el cuerpo y el token sigue siendo válido

Vulnerable

4.2 Ataque B: tokens de un teléfono sano usados por un bot

El atacante tiene un Android sano que genera tokens limpios. Un bot, un emulador o un teléfono rooteado (que por sí solos no pasarían MEETS_DEVICE_INTEGRITY) arma las peticiones y les pega esos tokens. Como el token no está ligado a la petición, el servicio solo ve "token válido de un dispositivo sano".

Ataque B: un teléfono sano como fábrica de tokens para un bot

Vulnerable

4.3 Ataque C: tokens viejos

Si el servicio no compara timestampMillis con la hora actual, el atacante puede guardar tokens sanos y usarlos horas después, incluso cuando el dispositivo ya está rooteado o comprometido. El veredicto describe el dispositivo al momento de generar el token, no al momento de usarlo.

Resultado Sin requestHash ni control de frescura, Android Tier 2 solo prueba que "existe un Android sano en algún lado", no que "esta petición viene de la app legítima, sin modificar y ahora". Es el mismo hueco que iOS Tier 2 sin recalcular el clientDataHash.

5. La corrección

5.1 Qué cambia

  1. La app calcula el hash con los datos de la petición y un timestamp, y lo pasa en setRequestHash(...). Envía el token y el timestamp, pero no el hash.
  2. APIM envía al servicio el resumen de la petición que recibió: método, ruta, SHA256(cuerpo), deviceid y timestamp.
  3. El servicio, después de descifrar el token:
    • recalcula el hash con la petición recibida y lo compara con requestDetails.requestHash;
    • comprueba que timestampMillis y el timestamp de la petición estén dentro de la ventana de frescura;
    • comprueba que requestPackageName y appIntegrity.packageName sean pe.ibk.personas;
    • valida los veredictos aceptables: PLAY_RECOGNIZED y MEETS_DEVICE_INTEGRITY.
requestHash = SHA256( método | ruta | SHA256(cuerpo) | deviceid | timestamp )   // 64 caracteres hex, menos que el máximo de 500 de Google

El costo es bajo: el proveedor ya está preparado por el warm-up, así que pedir el token con requestHash tarda lo mismo que sin él. Calcular un SHA256 es despreciable.

Decisión pendiente: el reenvío idéntico dentro de la ventana Con requestHash y timestamp, el único replay que queda es reenviar exactamente la misma petición en los segundos de la ventana. Google indica que las standard requests tienen una mitigación automática, pero no es un control que el banco gobierne. Si se quiere el mismo nivel que Huawei, se puede registrar el requestHash en Redis con SET NX y TTL igual a la ventana. Es opcional, y conviene decidirlo con el mismo criterio para las tres plataformas.
Riesgo residual: el relay Si el atacante controla un teléfono sano y modifica la app, puede pedir tokens con el requestHash de las peticiones que arma su bot. El requestHash no lo impide, pero lo vuelve caro: un token por petición, generado al momento. Lo mitigan el límite de peticiones por deviceid, PLAY_RECOGNIZED (detecta apps modificadas) y Tier 1 para lo crítico.

8. Cómo se implementa

8.1 App (Kotlin, ilustrativo)

// tokenProvider ya preparado al iniciar la app con prepareIntegrityToken (warm-up)
val ts = System.currentTimeMillis().toString()
val bodyHash = sha256Hex(bodyBytes)
val requestHash = sha256Hex(listOf(method, path, bodyHash, deviceId, ts).joinToString("|"))

tokenProvider.request(
    StandardIntegrityTokenRequest.builder()
        .setRequestHash(requestHash)
        .build()
).addOnSuccessListener { response ->
    request.header("X-TOKEN-INTEGRITY", response.token())
           .header("X-INTEGRITY-PLATFORM", "android")
           .header("X-INTEGRITY-TIMESTAMP", ts)
    // No se envía requestHash: lo recalcula el servidor
}

8.2 APIM: enviar el resumen de la petición

<set-variable name="bodyHash" value="@{
  var body = context.Request.Body?.As<string>(preserveContent: true) ?? "";
  using (var sha = System.Security.Cryptography.SHA256.Create()) {
    return BitConverter.ToString(sha.ComputeHash(System.Text.Encoding.UTF8.GetBytes(body)))
                       .Replace("-", "").ToLower();
  }
}" />
<send-request mode="new" response-variable-name="integrityResp" timeout="3" ignore-error="true">
  <set-url>{{integrity-service-url}}/deviceintegrity/evaluate/posture</set-url>
  <set-method>POST</set-method>
  <set-header name="Content-Type" exists-action="override"><value>application/json</value></set-header>
  <set-body>@(new JObject(
      new JProperty("platform",  "android"),

      new JProperty("path",      context.Request.OriginalUrl.Path),
      new JProperty("bodyHash",  (string)context.Variables["bodyHash"]),

  ).ToString())</set-body>
</send-request>

8.3 Servicio (pseudocódigo)

Decision evaluateAndroidPosture(Req r) {
    long now = clock.millis();
    if (abs(now - parseLong(r.timestamp)) > WINDOW_MS)       return deny("TIMESTAMP_STALE");

    Payload p = google.decodeIntegrityToken(PACKAGE, r.token); // v1/{packageName}:decodeIntegrityToken
    if (p == null)                                             return deny("TOKEN_INVALID");

    RequestDetails d = p.requestDetails;
    if (!PACKAGE.equals(d.requestPackageName))                 return deny("PACKAGE_MISMATCH");
    if (abs(now - d.timestampMillis) > WINDOW_MS)              return deny("TOKEN_STALE");

    String expected = sha256Hex(join("|", r.method, r.path, r.bodyHash, r.deviceId, r.timestamp));
    if (!constantTimeEquals(expected, d.requestHash))          return deny("REQUEST_HASH_MISMATCH");

    if (!PACKAGE.equals(p.appIntegrity.packageName)
        || !"PLAY_RECOGNIZED".equals(p.appIntegrity.appRecognitionVerdict))
                                                               return policyDecision("APP_NOT_RECOGNIZED");
    if (!p.deviceIntegrity.deviceRecognitionVerdict.contains("MEETS_DEVICE_INTEGRITY"))
                                                               return policyDecision("DEVICE_NOT_TRUSTED");

    return allow();
}

10. Ajustes al documento

  • En el diagrama Android Tier 2, cambiar "request Standard sin requestHash transaccional" por "request Standard con requestHash = SHA256(método | ruta | SHA256(cuerpo) | deviceid | timestamp)".
  • Cambiar "Valida package, timestamp y veredictos" por "recalcula requestHash con la petición recibida, valida requestPackageName, timestampMillis dentro de la ventana y veredictos".
  • Agregar X-INTEGRITY-TIMESTAMP a los headers y el resumen de la petición al llamado de APIM al servicio.
  • Definir la ventana de frescura (por ejemplo 60 a 120 s) y la serialización exacta, la misma para las tres plataformas.
  • Definir una política de transición para versiones de la app que aún no envían requestHash (por ejemplo, MONITOR durante un periodo).
